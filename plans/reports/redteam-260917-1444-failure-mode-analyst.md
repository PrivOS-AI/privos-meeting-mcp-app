# Red-team review — Failure Mode Analyst / Flow Tracer

Plan: `plans/260917-1358-meeting-agent-mcp-app-elevenlabs-diarization-voice-fingerprint/`
Perspective: Murphy's law on the end-to-end flow (record → end → upload → process → resolve speakers → summary → files → review).
Verdict: three of the plan's load-bearing browser-side assumptions are contradicted by the platform docs. The record/upload/review flow cannot run as written.

## Finding 1: Microphone is never granted to the iframe — the entire app is dead on arrival

- **Severity:** Critical
- **Location:** Phase 1, "Architecture › Manifest (trích)"; plan.md § "Manifest permissions (`privos-app.json`)"; Phase 2, "Luồng"
- **Flaw:** The tool's `_meta.ui` block declares only `resourceUri`, `hideAiChat` and `csp`. The platform grants camera/microphone **only** when the tool declares `_meta.ui.permissions`. No phase, no manifest excerpt, no todo, no success criterion mentions `permissions: ["microphone"]`. The permissions table in plan.md is entirely about Hub OAuth scopes (`files:*`, `db:*`, `rooms:read`…), which are a different mechanism and do not reach the iframe `allow=` attribute.
- **Failure scenario:** P1 and P2 are implemented and unit-tested green (mic is mocked in vitest). First manual test in a real room: the user clicks "Bắt đầu ghi", `getUserMedia` rejects with `NotAllowedError` in a sandboxed iframe that was never given `allow="microphone"`. Phase 2 step 10 responds to `NotAllowedError` by showing "hướng dẫn cấp quyền" — but there is nothing the user can do; the browser permission prompt never appears because the frame is not permitted to ask. Fixing it means editing the manifest and going through republish / version-bump + admin Refresh + approve (developer-guide.md:64), i.e. an admin round-trip discovered at the end of Phase 2, after 5 days of work.
- **Evidence:**
  - `~/projects/privos-dev-docs/mcp-app-platform/security-and-data-model.md:18` — "**Permissions**: camera/microphone only granted if declared in `_meta.ui.permissions`"
  - `~/projects/privos-dev-docs/mcp-app-platform/developer-guide.md:47` — `permissions: [],  // camera, microphone, etc.`
  - `phase-01-scaffold-app-foundation.md:71-72` — `"ui": { "resourceUri": …, "hideAiChat": true, "csp": {…} }` (no `permissions`)
  - `phase-02-live-recording-and-realtime-captions.md:43` — `getUserMedia({ audio: {...} })`; `:197` — "xử lý `NotAllowedError` mic → hướng dẫn cấp quyền"
- **Suggested fix:** Add `"permissions": ["microphone"]` to `_meta.ui` of `meeting_agent` in Phase 1 (not Phase 2), add it to the plan.md manifest section, and add a Phase 1 success criterion: "open the tool in a real room, call `navigator.mediaDevices.getUserMedia({audio:true})` from the console/dev button, confirm the prompt appears". This must be verified before any Phase 2 work starts, because it is manifest-approval-gated.

## Finding 2: The whole crash-recovery design sits on IndexedDB, which is unavailable in an opaque-origin iframe

- **Severity:** Critical
- **Location:** Phase 2, "Architecture › IndexedDB chunk store" + "Implementation Steps 2/13/14"; plan.md § "Acceptance criteria" bullet 1; plan.md § "Rủi ro chính" row "Tab đóng/crash khi đang ghi"
- **Flaw:** The app document is sandboxed **without `allow-same-origin`**, i.e. it runs in an opaque origin. The SDK docs state plainly that the app's own `localStorage` "throws or is wiped between loads" for exactly this reason, and that is why `app.storage` (a host-bridged key/value proxy) exists at all. `indexedDB.open()` in an opaque origin throws `SecurityError` in Chromium and returns null storage in Firefox — the same rule, same cause. The plan builds the authoritative recording branch (`MediaRecorder` chunks → IndexedDB), the crash-recovery banner, the "keep chunks until upload succeeds" safety net, and a top-line acceptance criterion on this store. Phase 1 even notes the opaque origin (`phase-01:28`) for asset bundling but never draws the storage conclusion.
- **Failure scenario:** 60-minute meeting, `ondataavailable` fires every 5s; `idbChunkStore.append` rejects on the first chunk (or silently on `open`). If append errors are swallowed (nothing in the plan says they are surfaced), the recorder keeps running, the REC timer keeps ticking, the caption keeps scrolling — and "End & summarize" produces a `Blob` of zero chunks, or the tab OOMs because the only fallback is to hold an hour of Opus in RAM. Either way the meeting is unrecoverable and the user only learns at the end. Tab crash mid-recording, the scenario this design exists for, loses 100% of the audio. `fake-indexeddb` in the Phase 2 unit test (step 2) passes happily and proves nothing about the sandbox.
- **Evidence:**
  - `~/projects/privos-dev-docs/mcp-app-platform/security-and-data-model.md:16` — "**Iframe sandbox**: deny-by-default — no `allow-same-origin`"
  - `~/projects/privos-dev-docs/mcp-app-platform/react-sdk-reference.md:125-128` — "The app document runs in a **sandboxed opaque origin**, so its own `localStorage` throws or is wiped between loads. `app.storage` proxies over the host bridge…"
  - `phase-02-live-recording-and-realtime-captions.md:15` (`MediaRecorder` → "mỗi Blob chunk ghi ngay vào IndexedDB (chống crash tab)"), `:89-99` (`ChunkStore`), `:189` (test via `fake-indexeddb`), `:244` ("Chunk chưa `clear` → recovery banner lần sau vẫn upload lại được")
  - `plan.md:29` — acceptance criterion "tab crash giữa chừng → mở lại khôi phục audio từ IndexedDB"
  - Secondary defect in the same design: `ChunkStore` (`phase-02:94-99`) keys only on `meetingId` and stores no `roomId`. The recovery banner mounts wherever the user next opens the app (`phase-02:201`), so an orphan recording started in room A is uploaded into whichever room is open — a cross-room disclosure of meeting audio.
- **Suggested fix:** Spike this on day 1 of Phase 1 (open a dev tool in a real room, call `indexedDB.open` and `new Blob` persistence from the iframe) before committing to the architecture. If it throws, the honest options are: (a) request an un-sandboxed/host-mediated storage surface from the platform team, (b) stream chunks to Files/`mcpapp.objects.put` as they are produced (content-addressed, 32 MiB cap per object — see tools-database.md:262 — so chunk it), or (c) drop the crash-recovery acceptance criterion and say so explicitly. In all cases persist `roomId` alongside `meetingId` and refuse to recover into a different room.

## Finding 3: The chunked-upload fallback cannot be implemented from the iframe, and the direct path pushes a 40-100MB base64 string through a 10s bridge

- **Severity:** Critical
- **Location:** Phase 2, "Architecture › Upload có fallback chunked" + Requirements bullet "Upload: direct `app.uploadFile` … ngược lại chunked"
- **Flaw:** Two independent breakages in one function.
  1. `upload-chunk` is `multipart/form-data` with a `file` part. The host bridge's `app.rest()` is a **JSON proxy that explicitly cannot tunnel multipart**; the only multipart path exposed to an iframe is `host/file.upload`, hard-wired to `file-management.files.upload` (direct). So `uploadChunked(init → chunk×N → complete)` has no transport from the iframe. The plan's own "Alternative" (keep chunks in IndexedDB and retry) does not help — there is no API surface to call.
  2. The direct path is `app.uploadFile({ base64Data })`. A 40MB webm becomes a ~54MB base64 JS string, structured-cloned across `postMessage` to the host, which then re-encodes it into a multipart body. Peak tab memory ~3× blob size, and the host-bridge response timeout defaults to **10 000 ms** with no documented per-call override on `uploadFile` (`timeoutMs` is documented on `app.rest`, not on `UploadFileParams`).
- **Failure scenario:** A 45-minute meeting (~25MB) may squeak through. A 2-hour meeting is ~50-60MB: base64 conversion freezes the tab for seconds, the upload exceeds the bridge timeout, the promise rejects, and per `phase-02:243` the chunks are retained — so the user retries and freezes the tab again, forever. A 2.5h+ meeting (>95MB) takes the `uploadChunked` branch, which is unimplementable, so it fails at the first `app.rest` multipart call with a 4xx/403. Note the plan's own constraint set targets 2-3h recordings (`plan.md:187`, Phase 5 "Transcript 3h", Phase 6 "cuộc họp 1h/3h") — the common case, not an edge case.
- **Evidence:**
  - `~/projects/privos-dev-docs/mcp-app-platform/auth-and-rest-integration.md:519-521` — "**Multipart upload** can't tunnel through the JSON proxy, so `host/file.upload` posts directly to `file-management.files.upload` as the user"
  - `~/projects/privos-dev-docs/mcp-app-platform/react-sdk-reference.md:114` — `base64Data | string | required — base64 content`; `:89` — "`timeoutMs` … host-bridge response timeout override (default 10000)"
  - `~/projects/privos-dev-docs/file-management/file-management-api.md:199-209` — `POST /file-management.files.upload-chunk`, `Content-Type: multipart/form-data`, `file | File | Yes`
  - `phase-02-live-recording-and-realtime-captions.md:29, 122-131` — `DIRECT_LIMIT = 95MB`, `uploadChunked(...)  // init → chunk(md5) → complete`
  - Also unmodelled: `upload-chunked-complete` requires a `finalChecksum` MD5 of the **whole** file (`file-management-api.md:230`), and `chunkSizes` are dictated by the server response (`:190`), not chosen by the client as `phase-02:194` assumes.
- **Suggested fix:** Decide the transport before writing Phase 2. Realistic option: have the **backend** own the upload — iframe streams/hands the blob to an app tool (or the recorder uploads per-chunk objects), and the server does the chunked multipart with bot credentials, exactly as the reference app does server-side (`~/projects/genealogy-privos-mcp-app/src/server/export/hub-file-upload.ts:141`). If the iframe must do it, cap supported meeting length at whatever `app.uploadFile` provably survives and state that cap in the acceptance criteria. Either way, add a Phase 2 success criterion that uploads a real 60MB blob end-to-end before the rest of Phase 2 is built.

## Finding 4: The declared CSP blocks the review flow — presigned transcript fetch and audio playback

- **Severity:** High
- **Location:** Phase 6, "Architecture › Tải transcript + audio" and "Player"; Phase 4, "UI › resolve-speakers-modal"; Phase 7, Non-functional "CSP của tool UI chỉ mở đúng `https://api.elevenlabs.io` + `wss://api.elevenlabs.io`"
- **Flaw:** The app-declared CSP is enforced on the iframe document. Phase 1 declares `connect-src: [api.elevenlabs.io, wss://api.elevenlabs.io]` and Phase 7 hardening freezes it there as a security requirement. But Phase 6 does `fetch(presignedUrl)` for `transcript.json` and sets `<audio src=presignedUrl>`, and Phase 4's speaker-sample player does the same. Presigned URLs point at the object store origin (MinIO/S3), which appears in neither `connect-src` nor `media-src` (never declared at all). The reference app deliberately does **not** do this: it *opens* the presigned URL as a navigation (`export-panel.tsx:11` — "this panel just opens that URL"), which CSP does not gate.
- **Failure scenario:** Phase 6 is built and demoed against the dev Hub. In the room tab, the meeting detail screen renders the header, then `fetch` is refused (`Refused to connect … violates Content Security Policy`) → transcript never loads → the virtualized list, the search, the speaker filter, the highlight-follows-playback, and the DOCX export (which needs `segments`) are all empty. The `<audio>` element fires `error`, which the plan interprets as "presigned URL expired" (`phase-06:84,182`) and retries the exact same blocked request once, then tells the user to reload the page — a misdiagnosis loop that will burn hours. Same failure hits the Phase 4 "play sample" button inside the speaker-confirmation modal, i.e. the voiceprint onboarding flow. The documented fallback (`phase-06:65`, binary download through `app.rest`) does not work either: `app.rest` is a JSON proxy.
- **Evidence:**
  - `~/projects/privos-dev-docs/mcp-app-platform/security-and-data-model.md:19` — "**CSP**: app-declared CSP from `_meta.ui.csp` enforced"
  - `phase-01-scaffold-app-foundation.md:72` — `"csp": { "connect-src": ["https://api.elevenlabs.io", "wss://api.elevenlabs.io"] }`
  - `phase-07-settings-hardening-tests-and-hodao-deploy.md:36` — "CSP của tool UI chỉ mở đúng `https://api.elevenlabs.io` + `wss://api.elevenlabs.io`"
  - `phase-06-history-and-meeting-detail-review.md:57-59` (`app.rest` meta → `fetch(url)`), `:62` (`resolveAudioUrl`), `:65` (binary fallback via `app.rest`), `:82-84` (`<audio>` + onError retry)
  - `phase-04-speaker-identity-and-voice-fingerprint.md:142` — "nút ▶ phát mẫu (dùng presigned URL + `currentTime`)"
  - `~/projects/genealogy-privos-mcp-app/src/ui/screens/export-panel.tsx:11,70` — reference app opens the URL instead of fetching it
  - `~/projects/genealogy-privos-mcp-app/src/server/export/hub-file-upload.test.ts:97-102` — the Hub can also return `downloadUrl: null`, so the "presigned always available" assumption is not safe either
- **Suggested fix:** Determine the object-store origin at Phase 1 and declare it in `connect-src` **and** `media-src` (parameterised per deployment if the origin differs between Hubs), or route transcript reads through a backend tool that returns the JSON (it is app data, not a user file — but mind MCP response size) and audio through a same-origin streaming path. Replace the Phase 7 hardening line with the actual allowlist rather than a claim that only ElevenLabs is reachable. Add a Phase 6 success criterion: "player plays and transcript loads inside the real room tab, not just the Vite dev page".

## Finding 5: `speaker_profiles` is global-scoped biometric data guarded only by a room check that every caller passes

- **Severity:** Critical
- **Location:** plan.md § "MCP tools" (`speaker_profile_list` / `_update` / `_delete`, `meeting_relabel_speaker`); Phase 4 "Tools"; Phase 7 Non-functional "Mọi tool backend xác minh `context.actor`… fail-closed khi `actor.roomId !== args.roomId`"
- **Flaw:** The only authorization rule stated anywhere in the plan is `context.actor.roomId === args.roomId`. For room-scoped collections that is meaningful. `speaker_profiles` and `app_settings` are **global** — one physical collection shared by every room of the workspace (`app_{appId}_{collection}`). A caller in room B trivially satisfies `actor.roomId === args.roomId` by passing their own room, then reads, renames, relinks, merges or hard-deletes voiceprint profiles created in room A by people they have no relationship with. The tools take `profileId` directly; no ownership, no room provenance, no membership test on the profile is described. `mergeProfiles` and `speaker_profile_delete` are destructive and irreversible (Phase 7 rollback explicitly notes voiceprints cannot be regenerated once audio is deleted). Same shape for `meeting_settings_set`: any room can rewrite the workspace-global `speakerMatchThreshold`, silently degrading identification for every other room.
- **Failure scenario:** Meeting Agent is installed workspace-wide. A member of a low-trust room opens Settings › Speaker identification, which calls `speaker_profile_list {roomId: <their room>}` and returns the full roster of every person ever enrolled anywhere in the workspace — names, linked PrivOS user ids, sample counts, last-seen dates. That is an org chart plus attendance metadata assembled from biometric records, exposed across rooms. A careless (or malicious) click on "Xoá toàn bộ voiceprint" (`phase-07:157`) destroys every profile in the workspace. The Phase 7 audit ("không response nào chứa vector") passes, because the leak is the metadata and the destructive write, not the vector.
- **Evidence:**
  - `~/projects/privos-dev-docs/mcp-app-platform/apis/tools-database.md:34` — `global` (default) → `app_{appId}_{collection}` → "Shared data across all rooms"
  - `plan.md:92` (`speaker_profiles | global`), `:117-119` (`speaker_resolve`, `speaker_profile_list/_update/_delete`, `meeting_relabel_speaker` — all keyed on `roomId` + `profileId` only)
  - `plan.md:99` — "Quyền ghi: … backend (bot credential) ghi … `speaker_profiles`, `app_settings`" (no per-room ownership model)
  - `phase-04-speaker-identity-and-voice-fingerprint.md:138` — "Mọi tool kiểm `context.actor.roomId === args.roomId` trước khi chạm dữ liệu" (the sole stated check)
  - `phase-07-settings-hardening-tests-and-hodao-deploy.md:34-35` — same check restated as the hardening rule, immediately followed by "`speaker_profiles` là dữ liệu sinh trắc"
  - Note the bot credential makes this worse, not better: the backend acts as the installation bot, so the Hub's own room-membership enforcement (`rest-tool-call.md:56`) never applies to the profile reads.
- **Suggested fix:** Either (a) make profiles room-scoped (the plan already has this as the fallback for open question #7 — take it for the authorization reason, not only the transport reason), or (b) add an explicit `roomIds[]`/`ownerRoomId` field on each profile and filter every list/update/delete/merge by "the caller's verified room appears in this profile's provenance". Add an explicit negative test to the Phase 7 matrix: user in room B calls `speaker_profile_delete` on a profile enrolled only in room A → denied. Decide whether `app_settings` is genuinely workspace-global (admin-only) or per-room before shipping a user-facing slider that writes it.

## Finding 6: Every "Xử lý lại" path is either unrunnable or double-runs the job

- **Severity:** High
- **Location:** Phase 3 "Queue" + Requirements bullets "Idempotent" / "Timeout" / "Xoá `audio.webm` sau khi job thành công nếu `keepAudio === false`"; Phase 5 Requirements bullet "Retry chỉ bước summary"; Phase 7 Risk "pm2 restart giữa job dài"
- **Flaw:** Three compounding defects on the retry path the UI advertises.
  1. `withTimeout(runMeetingJob(job), MEETING_JOB_TIMEOUT_MS)` is a promise race. It does not abort the ffmpeg child process, the in-flight ElevenLabs upload, the sherpa extraction, or the Hub writes. At timeout the record is marked `failed`, `running--` fires in `.finally`, and `pump()` starts the next job — while the "timed out" job is still executing.
  2. `meeting_process` on a `failed` record "reset record và chạy lại từ đầu" with no check that the previous execution has actually stopped. So the user's "Xử lý lại" button starts a second concurrent run of the same `meetingId`. Two runs then: write the same transcript files with `duplicateAction:'replace'` (interleaved, last writer wins, possibly a truncated file), call `replaceActionItems` twice, and both call `enrolEmbedding` on the same global profile. `enrolEmbedding` is read-modify-write over an `embeddings[]` array, and `mcpapp.db.update` takes a whole `data` object — there is no atomic array append, no compare-and-set, no transaction — so one run's enrolment is silently lost, or worse, the cap-20 recompute writes a stale centroid.
  3. With the default `keepAudio=false`, the job deletes `audio.webm` on success. Phase 5 makes a summarizer failure a **non-fatal** outcome: the job still finishes `completed`, sets `summaryError`, and the UI offers "thử lại". That retry re-runs the whole job, whose first step is to download an audio file that the previous run already deleted → guaranteed 404. The advertised recovery for the single most likely partial failure (LLM provider outage / 429) cannot work.
- **Failure scenario:** Anthropic returns 529s during a 3h meeting's reduce pass. Job completes with `summaryError`. User clicks "Thử lại" → `meeting_process` resets the record, enqueues, and the job dies at step `download` with "Không tải được file ghi âm từ Hub." The transcript is fine, the summary is permanently unobtainable, and the only remaining path is to re-record the meeting. Separately, on a 3h meeting the 1h default timeout fires, the UI shows `failed`, the user clicks retry, and now two jobs stream the same 350MB WAV to ElevenLabs — double cost, double diarization, competing file writes.
- **Evidence:**
  - `phase-03-post-meeting-diarization-pipeline.md:66` — "mỗi job bọc `withTimeout(runMeetingJob(job), env.MEETING_JOB_TIMEOUT_MS)`, `.catch` → `fail`, `.finally` → `running--; pump()`"
  - `phase-03-post-meeting-diarization-pipeline.md:25` — "`failed` → reset record và chạy lại từ đầu"; `:27` — timeout → failed; `:28`/`:196` — delete `audio.webm` when `keepAudio === false`
  - `phase-05-ai-summary-and-save-to-privos-files.md:34` — "job kết thúc `completed` với `summary: null` và cờ `summaryError`"; `:28` — "tool `meeting_process` chạy lại toàn bộ job"; `:203` — success criterion "Ngắt `ANTHROPIC_API_KEY` → job vẫn `completed` … + nút thử lại"
  - `phase-04-speaker-identity-and-voice-fingerprint.md:115` — `enrolEmbedding(...)  // push, cap 20 mới nhất, recompute centroid`
  - `~/projects/privos-dev-docs/mcp-app-platform/apis/tools-database.md:161-168` — `mcpapp.db.update { collection, id, data }` — whole-object write, no array operators, no transaction primitive anywhere in the tool list
- **Suggested fix:** (a) Give the job an `AbortController` threaded into ffmpeg spawn and every fetch, and have the timeout abort rather than merely reject; keep a process-local `Set<meetingId>` of in-flight runs and refuse `meeting_process` while a run is live regardless of DB status. (b) Do not delete audio until the job's summary step has succeeded, or keep audio until the user has seen the summary — deleting the only reprocessable input at the end of a partially-failed job is data loss by design. (c) Make the summary retry a separate tool (`meeting_summarize {meetingId}`) that starts from the already-uploaded `transcript.json`, which also removes the double ElevenLabs charge. (d) Serialize profile writes behind a single in-process mutex and re-read before write.

## Finding 7: A pm2 restart leaves the user staring at a progress bar forever

- **Severity:** High
- **Location:** Phase 3, Requirements bullet "Job treo do process restart" + "Queue"; plan.md § "MCP tools" (`meeting_status` output); Phase 7, Requirements "Functional — job dọn dẹp"
- **Flaw:** The queue is in-process with no persistence of `pending` (`phase-03:66`). On restart, everything queued but not started is gone and everything running is orphaned in `processing_jobs` with `status='processing'`. The only recovery is `sweepStale`, which runs **inside `meeting_bootstrap {roomId}`** — a tool the iframe calls once at mount. Meanwhile `meeting_status` returns `{status, step, progress, error?, result?}` and deliberately does **not** expose `heartbeatAt`, so the polling UI has no way to tell "still working" from "the process died 40 minutes ago". The processing screen polls every 3s and has a "Xử lý lại" button only in the `failed` state.
- **Failure scenario:** User ends a 90-minute meeting, job starts, they keep the tab open watching the 6-step progress. Ops restarts pm2 (deploy, `max_memory_restart: '2G'` tripping on a long transcript, OOM). The job record stays `processing` at step `transcribe`, 40% forever. The already-mounted iframe never calls `meeting_bootstrap` again, so `sweepStale` never fires; `meeting_status` keeps returning the same frozen record; the UI shows no error and offers no retry. The user waits, refreshes, and only then (new mount → bootstrap → sweep) sees `failed(interrupted)`. Queued-but-not-started jobs are worse: they were never in the DB queue, they are simply lost, and `meetings.status` stays `uploading`/`processing` with nothing to sweep.
  This is compounded by a factual error driving the design: the plan asserts the tool-call endpoint "luôn nhận `roomId` và kiểm tra membership", which is why both the stale-job sweep and the audio-retention purge are per-room and user-triggered. The endpoint documents `roomId` as **optional**, so a boot-time, workspace-wide sweep over global state is likely available and was never evaluated.
- **Evidence:**
  - `phase-03-post-meeting-diarization-pipeline.md:30` — sweep only via `meeting_bootstrap {roomId}`; `:68` — "không quét lúc boot vì `roomId` chỉ biết khi có phòng"
  - `plan.md:116` — `meeting_status` → `{ status, step, progress, error?, result? }` (no `heartbeatAt`, no staleness signal)
  - `phase-03-post-meeting-diarization-pipeline.md:29` — UI polls every 3s, "nút 'Xử lý lại' khi `failed`" only
  - `plan.md:190` — "endpoint luôn nhận `roomId` và kiểm tra membership" vs `~/projects/privos-dev-docs/mcp-app-platform/apis/rest-tool-call.md:22` — "`roomId` | string | **No** | Room context for the tool execution" and `:56` — membership is validated only "When `roomId` is provided"
  - `phase-07-settings-hardening-tests-and-hodao-deploy.md:30` — retention scan inherits the same false constraint: "phòng chưa ai mở kể từ lần boot gần nhất chỉ được quét khi có người mở app"
  - `phase-07-settings-hardening-tests-and-hodao-deploy.md:203` — success criterion assumes restart-mid-job resolves itself ("job kết thúc hoặc `failed(interrupted)`")
- **Suggested fix:** Return `heartbeatAt` (or a server-computed `stale: boolean`) from `meeting_status` and let the processing screen surface "job đã dừng" + retry after ~2 missed heartbeats — that alone fixes the user-visible hang regardless of the sweep schedule. Persist the pending queue by loading `processing_jobs` with `status='queued'` on startup. Empirically test `mcp-apps.tool-call` **without** `roomId` in Phase 1 (same spike as the global-scope question, open question #7) and, if it works, make the sweep and the retention purge boot-time and workspace-wide instead of "whenever someone happens to open the app".

## Finding 8: The caption branch posts a WebSocket frame every 8ms with no buffering and no backpressure, for up to 3 hours

- **Severity:** High
- **Location:** Phase 2, "Architecture › PCM16 worklet" + "Realtime client"; Phase 2 Non-functional "Ghi liên tục 60 phút không rò bộ nhớ"
- **Flaw:** `Pcm16Processor.process()` is invoked once per render quantum (128 frames). The plan's worklet calls `this.port.postMessage(out)` on every invocation, and `realtime-scribe-client` sends each `Int16Array` as a base64 `input_audio_chunk`. At 16kHz that is ~125 messages/second — 256 bytes of PCM inflated to a ~344-byte base64 string inside a JSON envelope, i.e. ~43KB/s of frames and 1.35 million messages over a 3-hour meeting, each one a main-thread JSON+base64 encode competing with React rendering the caption list. Nothing in the plan buffers to a sane chunk size (100-250ms), and nothing checks `ws.bufferedAmount` before sending.
- **Failure scenario:** Meeting room wifi degrades (very common — this is the offline-meeting use case). The socket stops draining; `send()` keeps queueing because the plan never inspects `bufferedAmount`; the browser's outgoing buffer grows unbounded at 43KB/s while the caption UI freezes. The MediaRecorder branch, advertised as independent of the WS, is not independent of the tab: it shares the heap and the main thread.
